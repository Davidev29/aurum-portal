# Avaliação — Documentação, ADRs e Cobertura de Testes (AurumBit Portal 0.1.0)

**Data:** 2026-11-12 · **Escopo:** revisão somente leitura de `docs/` (USER_GUIDE, SECURITY, PRIVACY, TERMS, SUPPORT, COLOR_SYSTEM, motion-system, `docs/adr/*`), `README.md`, `tests/`, `vitest.config.ts`, `.github/workflows/ci.yml` — cruzados com o código (`electron/`, `shared/`, `src/`, `scripts/`). Nenhum arquivo do repositório foi modificado; apenas este relatório foi criado.
**Legenda:** S1 = bloqueador/exposição de release; S2 = significativo, corrigir antes de distribuir; S3 = corrigir em seguida; S4 = nit.

## Veredito: CONCERNS

A documentação jurídica/de segurança é, em geral, **honesta e precisa**: as alegações centrais sobre o cofre (AES-256-GCM, HKDF-SHA-256, AAD `tabela:id:campo`, Argon2id 64 MiB/3 iter, `.pvbackup` só-export, `idleLockMinutes`/`retainAuditDays` não implementados, `chain_incomplete` não calculado) batem com o código. **Contudo**, há um conjunto de divergências S2 entre o que os guias prometem e o que o build atual entrega — um botão de bloqueio que não existe, uma tela "Acessos" que não existe, 11 portais embutidos omitidos, envio automático de formulário por padrão documentado como "sempre manual", e uma TSA "configurável em Configurações" que está oculta na UI — além de um gate de cobertura cosmético e de stress/e2e nunca executados no CI. Não é FAIL (nenhum achado S1: nenhuma alegação de criptografia fabricada, nenhum vazamento documentado), mas a documentação **não está pronta** para acompanhar uma distribuição 0.1.0 sem correções. O README foi reescrito **durante esta revisão** (mtime 2026-11-12 19:38); as linhas citadas referem-se ao arquivo no disco no momento da leitura.

## Pontos fortes (bullets)

- **Cofre/criptografia exatamente como documentado** — `electron/main/vault/crypto.ts:40-57` (AES-256-GCM, IV 12 B, tag 16 B, envelope `pv1:`), `:92-95` (AAD `tabela:id:campo`), `vault/backup.ts:21-40` (Argon2id 64 MiB, 3 iterações, paralelismo 1, frase-senha ≥ 12), `vault/key-store.ts:25-56` (DPAPI/safeStorage, 32 B, `vault.key`) — batem com SECURITY.md:105-110 e ADR 0004.
- **Redaction verificada no caminho real** — `db/repositories/audit.ts:32` aplica `redactRecord` antes do insert; `security/redaction.ts:8-44` (URLs com parâmetros sensíveis, PEM/blobs, profundidade > 6); sessões logam `redactUrl(...)` (`sessions/manager.ts:512`, `selection.ts:46-103`, `index.ts:446`).
- **A3/PIN recusado de verdade** — `sessions/selection.ts:140-147` lança erro e loga só `hostname`/`tokenName`, nunca o PIN; nenhuma alegação de suporte A3 em nenhuma doc.
- **Limitações documentadas são reais** — `idleLockMinutes` e `retainAuditDays` não aparecem em nenhum lugar de `electron/` (grep vazio), como declaram README/SECURITY/TERMS/USER_GUIDE; `chain_incomplete` não é calculado (`shared/constants.ts:167` só registra o status); `.pvbackup` não tem caminho de restauração na interface.
- **ADR 8/8 consistentes** — títulos e status ("Aceita") no `docs/adr/README.md` correspondem aos arquivos; ADR 0006 (host:porta sem esquema), ADR 0007 (opt-in CNPJ) e ADR 0008 (PAdES incremental, pkijs, `<nome>-assinado`, 50 MB, token de doc 15 min em `shared/signature.ts:137`, fila única via flag `pdfSigning` em `ipc/index.ts:1297-1302`) batem com o código.
- **Inventário honesto de limitações** — guias pedem verificação externa (validar.iti.gov.br), admitem que o teste de injeção não garante aceitação do portal, e PRIVACY/SECURITY/TERMS exigem revisão jurídica antes de distribuição; nenhuma alegação de "seguro" absoluto.

## Achados

### S2 — significativo, corrigir antes de distribuir

**D-1 — S2 — `docs/USER_GUIDE.md:46`** — O guia afirma que o rodapé da barra lateral exibe **"Bloquear e fechar sessões"** (encerra janelas e registra o evento). O botão **não existe**: `src/components/app-shell.tsx:24-48, 87-140, 142-177` não tem rodapé com essa ação, e a API `aurumBitPortal().app.lock()` não tem nenhum chamador em `src/` (grep vazio) — o handler `app:lock` (`electron/main/ipc/index.ts:1184-1189`) é IPC morto para a UI atual.
*Impacto:* a única ação manual de bloqueio documentada é inacionável; usuário conclui que o recurso não existe ou acha instruções inválidas; enfraquece a postura de segurança do guia.
*Recomendado:* ou reintroduzir o botão no sidebar (chamada a `app.lock`), ou corrigir o guia para o estado real (bloqueio manual inexistente; usar o bloqueio do Windows).

**D-2 — S2 — `docs/USER_GUIDE.md:242-250`** — A seção **"7. Abrir uma sessão → Por Acessos (certificado primeiro)"** manda "Abra **Acessos** no menu", selecionar certificado e clicar "Avançar para os portais". Não há rota `src/app/acessos`, nem item "Acessos" na navegação (`app-shell.tsx:24-48`), nem grep positivo em `src/` ou `electron/`. A tela foi removida/renomeada (fluxo hoje vive na Store).
*Impacto:* o guia de uso principal aponta para uma tela inexistente; falha de onboarding para o fluxo mais sensível do produto (seleção de certificado).
*Recomendado:* reescrever a seção para o fluxo real pela Store ("Abrir" → método Certificado), removendo "Acessos".

**D-3 — S2 — `docs/USER_GUIDE.md:174-190` e `README.md:123-141`** — As tabelas "Serviços embutidos" listam 12 serviços e **omitem os 11 portais SpeedGov municipais** embutidos e semeados (`shared/builtins.ts:994-1055`; `electron/main/db/seed.ts:23`); usuários não descobrem no guia metade do catálogo senha-first. Divergências adicionais: JUcec-CE documentada como "Senha" (`USER_GUIDE.md:181`), mas o código usa `certificate` + `password` com defaultAuth `certificate` (`shared/builtins.ts:805-824`); itens nativos "DET Trabalhista | Senha" vs `certificate+password` default certificate (`builtins.ts:893-909`); "Redesim | Certificado" vs `certificate+password` (`builtins.ts:771-783`).
*Impacto:* catálogo documentado incompleto/errado; operadores compram fluxo de login errado para o portal errado.
*Recomendado:* gerar as tabelas a partir de `BUILTIN_SERVICES` (ou script de sync) e atualizar USER_GUIDE/README.

**D-4 — S2 — `docs/USER_GUIDE.md:191`, `:202`, `:281`; `README.md:109-110` (e README anterior)** — Claims de envio manual: "As automações de login são assistidas: o aplicativo preenche campos, mas **não envia o formulário automaticamente**" (191); "Login e senha — ...você clica em Entrar" (202); "O envio é **sempre manual**" (281); README: "**envio sempre manual por padrão**". O código faz o oposto por padrão nos serviços gerados: `buildAutoRecipe` emite `autoSubmit: true` para senha/antigos personalizados e SpeedGov (`shared/custom-service.ts:248-258`, `shared/builtins.ts:736-748`), e o agente clica em "Entrar" quando `autoSubmit` (`recipes/agent.ts:172,261-263`, `recipes/runner.ts:277-289`, `sessions/manager.ts:1004-1020`). A opção existe ("Entrar sozinho", `service-form-dialog.tsx:549-556`), mas com default ligado — o guia nem sempre o deixa claro (228 admite, 191/202/281 contradizem).
*Impacto:* alegação de segurança enganosa: o usuário acredita que o app nunca submete credenciais; na prática submete. Em portal com MFA/captcha, a análise de risco do operador fica errada.
*Recomendado:* unificar a redação com o comportamento real ("automação preenche e, por padrão, clica em Entrar em serviços de senha gerados; desligue Entrar sozinho para revisar"), e revisão jurídica/segurança do texto.

**D-5 — S2 — `docs/USER_GUIDE.md:482`, `docs/SECURITY.md:99`, `docs/adr/0008-pdf-signature-pades.md:20,46`, `README.md:314`** — Claims de que a TSA pode ser trocada em **Configurações** e testada com o botão **"Testar TSA"**. A seção "Assinaturas digitais (PAdES-B-T / TSA)" está **oculta na UI** do build atual (`src/app/settings/page.tsx:776`, comentário: "oculto da UI; valores (signTsaUrl, signStampReason) preservados no draft"); o handler `pdf.testTsa` existe (`ipc/index.ts`), mas não há caminho na interface para o operador seguir a instrução. O ADR 0008 também promete "URL editável em Configurações com botão Testar TSA".
*Impacto:* o operador é instruído a trocar para uma TSA ICP-Brasil credenciada — impossível no build; fica preso à DigiCert pública, ou desiste do fail-closed ao assinar às cegas.
*Recomendado:* restaurar a seção de TSA em Configurações (ou corrigir os quatro documentos e marcar explicitamente como indisponível na 0.1.0).

**D-6 — S2 — `.github/workflows/ci.yml:46-59`; `vitest.config.ts:17-37`** — CI roda typecheck, lint, format:check, `npm test` e build — **jamais** `test:coverage`, `test:stress` ou `test:e2e`. Registrado, não executado: e2e completo (`tests/e2e/`, 5 specs / 8 casos, incluindo `obligations-month-view.spec.ts` — o único teste ponta-a-ponta da visão do mês de Obrigações) fica **fora do gate de merge**; idem a suíte de stress (15 casos, Argon2id/PAdES em lote/agendador com 10 800 avisos). Cobertura exibida em `coverage/coverage-summary.json` (97,94% linhas, acima dos limiares 80/80/75) é medida apenas no subconjunto `include` de 16 arquivos — os módulos mais arriscados (`electron/main/ipc/index.ts` 1 547 linhas, `sessions/manager.ts` 1 501, `certificates/service.ts` 1 025, `windows-store.ts` 352) **não entram na métrica**.
*Impacto:* regressões em fluxos críticos (seleção de certificado, baixa de obrigações, assinatura PAdES) só são detectadas manualmente; o número de cobertura do repositório superestima a proteção real; o gate de thresholds nunca é exercido.
*Recomendado:* job (ou nightly) com `test:coverage` + thresholds aplicáveis e `test:e2e` em `windows-latest`; ampliar `coverage.include` para `electron/main/{ipc,sessions,certificates,db}/**`; ou documentar explicitamente que o CI é unitário+build e que stress/e2e são pré-release manuais.

**D-7 — S2 — `tests/` (ausência de testes de IPC)** — **Nenhum** teste importa `electron/main/ipc/*`: `registerIpcHandlers`, `assertTrustedSender` (frame principal apenas — `ipc/index.ts:210-217`), throttles de 800 ms (`:724-736`), mapeamento de erros para payloads controlados (`toErrorResponse`) e os caminhos de auditoria de eventos sensíveis (`session.opened`, `pdf.signed` com TSA host, `certificate.not_offered`) não têm cobertura de unidade; a fronteira só é exercida por e2e, que o CI não roda (ver D-6). `sessions/manager.ts` (1 501 linhas, allowlist/redirect/`will-download`/`select-client-certificate`) também não tem teste de unidade direto — apenas `security/redaction` e `certificates/core` (via chaos tests) cobrem decisões análogas.
*Impacto:* mudanças de wiring de IPC passam no CI sem quebra; a allowlist e o bloqueio de downloads são os controles mais dependentes de código não testado.
*Recomendado:* testes de unidade com Electron mockado (como `windows-store.test.ts` simula PowerShell) para `assertTrustedSender`, throttle, e `SessionManager.isAllowedUrl`/bloqueio de download; ou e2e obrigatório em CI.

**D-8 — S2 — `docs/PRIVACY.md:49-56` e `:101-103`** — O LGPD diz "Há **dois fluxos externos**" (portais + updates) e "O aplicativo **não transfere dados para o exterior por si só**". Faltam, no mínimo: (1) `brasilapi.com.br` ao importar certificado CNPJ — opt-in, mas um fluxo externo real (SECURITY.md:98 admite); (2) **TSA DigiCert** (`timestamp.digicert.com`, padrão) — a cada assinatura, o imprint SHA-256 vai a um provedor dos EUA (`pdf/timestamp.ts:8-11,62-70`); (3) fetch de **favicon** de qualquer domínio ao cadastrar/buscar logomarca (`services/logo.ts:82,105-119`). PRIVACY não menciona nenhum dos três, apesar de PRIVACY ser o documento LGPD.
*Impacto:* inventário de tratamento/transferência incompleto e juridicamente enganoso; o DPO/operador não consegue cumprir obrigação de informação sem ler SECURITY.md+código.
*Recomendado:* listar os três fluxos em "Compartilhamento" e "Transferência internacional" (com opt-in, mascaramento, base legal), espelhando o inventário do SECURITY.md:96-101.

**D-9 — S2 — `README.md:192,263` (atual); `README.md` (anterior) e `docs/qa/QA-STRESS-REPORT.md:24`** — "**497/497** testes unitários" não é reproduzível do tree: contagem estática de `it(` em `tests/unit/**/*.test.ts` (36 arquivos) dá **452** casos (sem `it.each`); nada verifica 497 em nenhuma automação (CI não roda cobertura; nada em `package.json` mostra 497). O número sobreviveu ao stress report sem fonte conferível.
*Impacto:* métrica de qualidade inflada/não verificável num README público no repositório; se 452 é o real, a divergência é de 10%.
*Recomendado:* medir e publicar o número real (`vitest run --reporter=verbose`) ou remover a contagem exata; fazer do `test:coverage` (com thresholds) o gate oficial.

**D-10 — S2 — `electron/main/certificates/icp-chain.ts:82-104`** — Módulo **morto** que baixa URLs do AIA por `fetch` e **instala certificados no repositório do Windows** (`CurrentUser\CA`), jamais importado em lugar algum (grep vazio). SECURITY.md:76 e README alegam "o app não instala raízes ICP-Brasil" — verdadeiro só porque o código está desconectado.
*Impacto:* código latente que, se ligado por descuido, baixa e instala raízes de CAs arbitrárias (a AIA vem do próprio certificado, de fonte não autenticada) sem confirmação do operador — exatamente o anti-padrão que SECURITY.md proíbe; e contradiz a promessa documentada se qualquer chamador futuro surgir.
*Recomendado:* remover o módulo ou movê-lo atrás de um flag explícito com ADR próprio; enquanto existir, documentar como pendência no relatório de dívida técnica.

### S3 — corrigir em seguida

**D-11 — S3 — `docs/COLOR_SYSTEM.md` (inteiro) vs `src/app/globals.css:42,57,65,109,124,132-133`** — O documento se apresenta como **"Estudo de colorimetria aplicado a `globals.css`"**, mas descreve um tema **azul** (`--pv-bg #F4F5F7/#0A0D13`, accent `#2B4BC8`, texto `#0F1B2D`, `--pv-accent-solid #243C9E`) que não existe no código: o tema atual é **neutro quente + champanhe** (`--pv-bg #eceae5/#1b1a17`, texto `#26241f/#ece9e2`, `--pv-accent-solid #c9a962`, `--pv-on-accent` sobre champanhe). Toda a tabela de tokens, o "Regra de ouro" e as razões de contraste citadas (≥ 12:1 texto, ≥ 4.5:1 faint, branco 9.5:1 sobre accent-solid) descrevem um sistema substituído.
*Impacto:* qualquer dev que seguir o doc aplica/auditará cores erradas; o claim de conformidade WCAG 2.2 AA não é auditável contra o CSS real.
*Recomendado:* reescrever COLOR_SYSTEM.md a partir do `globals.css` atual (ou remover a tabela) e validar os pares de contraste no tema quente.

**D-12 — S3 — `docs/SECURITY.md:58`** — A CSP documentada (`default-src 'self'; object-src 'none'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'; connect-src 'self'`) omite `script-src 'self' 'unsafe-inline'` e `style-src 'self' 'unsafe-inline'` **realmente aplicadas** (`electron/main/index.ts:440-442`). "CSP restritiva" continua funcionalmente restrita (sem remote scripts), mas a política real é mais permissiva em XSS inline do que o doc descreve.
*Impacto:* análise de risco baseada no doc subestima a exposição a XSS inline no renderer estático.
*Recomendado:* citar a CSP completa em SECURITY.md; idealmente eliminar `unsafe-inline` (nonces/hash) como débito conhecido.

**D-13 — S3 — `docs/SECURITY.md:59`** — "**DevTools desabilitado no aplicativo empacotado; F12 bloqueado nas sessões.**" Verificado: a janela principal usa `devTools: isDev` ✓ (`index.ts:349`), mas a janela de sessão e a `WebContentsView` do portal usam **`devTools: true` hardcoded** (`sessions/manager.ts:368,389`); só o handler `before-input-event` bloqueia F12 e **somente** `app.isPackaged` (`:745-749`). `Ctrl+Shift+I`/contexto não são bloqueados nessas views; popups usam `!app.isPackaged` (`:828`).
*Impacto:* alegação de mitigação mais forte que a realidade; DevTools alcançável em produção na janela de sessão.
*Recomendado:* `devTools: !app.isPackaged` nas views de sessão (ou documentar a exceção); reforçar para blocklist+shortcut completo.

**D-14 — S3 — `README.md:52` ("Destaques 0.1")** — "carimbo de tempo RFC 3161 **opcional**". Falso para a assinatura qualificada: sem TSA válida a assinatura é **bloqueada** (fail-closed) — `timestamp.ts`, `settings.ts:153-159` (`signTsaUrl` obrigatória, apenas URL configurável), ADR 0008 rejeitou explicitamente PAdES-B-B. O TSA é configurável, não opcional.
*Impacto:* expectativa errada sobre validade probatória; "assinar sem carimbo" não existe na build.
*Recomendado:* trocar "opcional" por "padrão obrigatório (fail-closed, TSA configurável)".

**D-15 — S3 — `README.md:125-138` e `:140-141` (e README anterior)** — Tabela "Portais embutidos" inventa taxonomia e dados: categorias ("Empresas", "Fiscal", "Trabalhista", "Financeiro") vs `Governo Federal/Estadual/Prefeituras` do código; "eSocial — pendências Receita (CNPJ)" vs nome real **"Pendências CNPJ"** (`builtins.ts:828`) em categoria Governo Federal (não Fiscal); "Simples Nacional | Fiscal" vs Governo Federal (`builtins.ts:933-936`); "Registrato | Financeiro | Certificado" vs Governo Federal e `certificate+password` (`builtins.ts:954-968`); "eSocial | Trabalhista | Certificado" e "DET Trabalhista | Trabalhista | Senha" vs `certificate+password` ambos (`builtins.ts:870-909`). Ver D-3 para a omissão dos SpeedGov.
*Impacto:* tabela de vendas/marketing do README diverge do seed real; em pré-venda técnica, quebra a confiança.
*Recomendado:* sincronizar a tabela com `BUILTIN_SERVICES` (nome, categoria, authMethods/defaultAuth) num script de docs.

**D-16 — S3 — `docs/USER_GUIDE.md:39` e e2e vs o que o guia promete** — A visão do mês (calendário com situação, modal do dia, feriados + ícone/cor) está corretamente documentada e há e2e cobrindo-a (`tests/e2e/obligations-month-view.spec.ts`), **mas** esse spec depende de fixture com backdating (`updateLink dataInicio 2020-01-01`) e nunca roda em CI (D-6); a suíte unitária de 795 linhas (`obligations.test.ts`) cobre repositórios/agendador, não a UI. Fraude/regressão visual do calendário passa silenciosa.
*Impacto:* a "obrigação" mais visível do produto sem gate automatizado; regressão descoberta por usuários.
*Recomendado:* executar `test:e2e` no CI (windows-latest já é a base de `ci.yml`) ou, no mínimo, no pré-release; fixar o spec ao PR.

**D-17 — S3 — `tests/` (Windows store real)** — `windows-store.test.ts` cobre apenas helpers puros (`buildExportScript`, `normalizeSha1`, `parseWindowsCertificateRecords`); o fluxo real — listar/importar/instalar/remover em `CurrentUser\My` via PowerShell (`windows-store.ts`, ~352 linhas), incluindo a regra "falha se certificado em uso por sessão aberta" e a confirmação `REMOVER` — não tem nenhum teste automatizado (unit ou e2e); export transient PAdES também só indireto.
*Impacto:* os caminhos que mais mexem com repositório do Windows (e podem corromper certificados do usuário) dependem de verificação manual.
*Recomendado:* e2e em VM Windows descartável no pré-release (`npm run test:e2e` + script de assert de `Get-ChildItem Cert:\CurrentUser\My`); mínimo: testes com `child_process.spawn` mockado aferindo o script gerado para install/remove.

### S4 — nit

**D-18 — S4 — `electron/main/logger.ts:28-33`** — O caminho `errorToast` loga `error.stack` (até 4 000 chars) **sem** passar por `redactRecord`, contrariando a afirmação de que "Logs ... passam por redaction" (SECURITY.md:116-117; PRIVACY.md:26). Stacks raramente carregam segredos, mas exceções vindas do parsing de PFX/certificados podem ecoar dados.
*Recomendado:* aplicar `redactString`/truncamento ou remover `stack` do payload.

**D-19 — S4 — `docs/adr/0005-secrets-encryption.md`** — "`autoSubmit` é `false` por padrão": verdadeiro para o *schema* (`shared/recipe.ts:41`, `recipe.ts`), falso para a *receita gerada* (true — ver D-4). ADR sem data de revisão; o parágrafo deveria refletir a matriz real.
*Recomendado:* acrescentar "(que é como nascem as receitas de serviços de senha geradas automaticamente — ver ADR 0006/custom-service)".

**D-20 — S4 — `docs/USER_GUIDE.md:476`** — "Abra **Assinaturas** no menu": o rótulo real na navegação é **"Assinar documentos digitalmente"** (`app-shell.tsx:37`); a sigla/seção é `/assinaturas`. Cosmético, mas reforça a sensação de doc desatualizado.
*Recomendado:* alinhar o rótulo.

**D-21 — S4 — `docs/USER_GUIDE.md:153` vs `electron/main/certificates/service.ts:425`** — Claim "máximo de 20 MB por arquivo" — verificado (`info.size > 20 * 1024 * 1024` rejeita). OK nesta verificação; registrado aqui apenas para rastreabilidade da checagem item a item. Nenhuma ação.
